# study

기술 주제 하나를 받아 그것에 대한 **개념·사용법·이슈**를 번호 매긴 Markdown 문서로 정리한 docs 레포를 만든다.
비교표 중심 `README.md`와 작성 컨벤션 `CLAUDE.md`를 세팅하고, git을 초기화해 **문서 단위로 한글 커밋**한다.
필요하면 사용자 확인을 받아 코드 예제까지 만들고, 산출물이 올바른지 검증·보완한다.

문서는 **항상 현재 작업 디렉토리**에 만든다. 별도 경로로 옮기지 않는다.

핵심 태도: 사실 기반으로 쓰고, 모르면 "확인 필요"라고 명시하고, 임의로 문서를 양산하지 않는다.
각 단계에서 애매하면 추측하지 말고 사용자에게 물어본다.

## 워크플로

아래 9단계를 순서대로 따른다. **커밋은 이 순서를 그대로 따른다** — 즉 CLAUDE.md가 최초 커밋, 그다음 문서들, 그다음 README, 마지막에 검증 보완 커밋. 별도의 "권장 순서"는 없다.

### 1. 주제·범위 파악

- 사용자가 말한 주제를 **한 줄로 확정**해 되읽어 준다. (예: "주제: NestJS의 Dependency Injection")
- 다룰 하위 항목(개념 / 동작원리·아키텍처 / 사용법 / 이슈·한계)이 애매하면 `AskUserQuestion`으로 범위를 좁힌다. 물어볼 것 예시: 깊이(입문 요약 vs 심화), 독자(처음 보는 사람 vs 이미 아는 사람), 코드 예제 필요 여부, 특정 버전/환경 한정 여부.
- **코드 예제가 필요하다고 하면 여기서 언어/프레임워크/라이브러리를 조사 → 선택받는다.** 문서(특히 사용법)가 이 선택에 맞춰 작성·커밋되므로, 6단계가 아니라 **문서를 쓰기 전 이 시점**에 정해야 한다(나중에 정하면 이미 커밋된 문서를 다시 고쳐야 함).
  - 주제에 흔히 쓰이는 언어·프레임워크·라이브러리를 조사한다(주제 특성, 공식 문서, 생태계 표준 기준). 라이브러리/SDK는 `context7`(`resolve-library-id` → `query-docs`)로 실재·버전을 확인하고, 없으면 `WebSearch`로 폴백한다.
  - 조사 결과를 후보로 정리해 `AskUserQuestion`으로 선택받는다(각 선택지에 용도·차이 한 줄). 언어/프레임워크/핵심 라이브러리를 각각 물어도 된다.
  - **원하는 게 후보에 없으면 사용자가 직접 입력**할 수 있게 한다("Other" 자유 입력). 추측으로 단정하지 말 것.
  - 선택된 언어·프레임워크·라이브러리(및 버전)를 한 줄로 되읽어 확정한다. 이 조합을 이후 문서·예제 전체에서 일관되게 쓴다.
  - 사용자가 이 시점에 정하기 어렵다고 하면 6단계로 미룬다(이 경우 사용법 문서는 언어 비종속으로 쓰고, 예제만 나중에 붙인다).
- 주제가 비었거나 너무 막연하면 먼저 무엇을 정리할지 되묻는다. 임의로 시작하지 않는다.

### 2. 대상 위치·git 상태 확인

- 현재 디렉토리를 대상으로 한다. `pwd`로 위치를 보여주고 여기에 만들 것임을 알린다.
- `ls -A`로 기존 파일 확인. 덮어쓸 수 있는 파일(`README.md`, `CLAUDE.md`, 같은 이름 문서)이 이미 있으면 **반드시 먼저 보고하고 확인**을 받는다. 그냥 덮어쓰지 않는다.
- git 상태를 점검한다:
  - `git rev-parse --show-toplevel 2>/dev/null` — 결과가 **현재 디렉토리와 다르면** 상위 레포의 하위에 있는 것이다. 이때는 사용자에게 "상위 레포에 커밋할지 / 여기서 새로 `git init` 할지" 묻는다. 의도치 않게 부모 레포에 섞지 않는다.
  - git 레포가 아니면 4단계 직전에 `git init -b main` 한다고 알린다.
  - 이미 레포면 `git status --short`로 기존 staged/dirty 변경을 확인한다. 무관한 변경이 있으면 보고하고 건드리지 않는다(이 스킬은 자기가 만든 파일만 스테이징).
- **git 사용자 설정 확인**: `git config user.name`과 `git config user.email`. 둘 중 하나라도 없으면 커밋이 실패하므로, 사용자에게 값을 묻거나(설정해도 되는지 확인 후 `git config`) 매 커밋을 `git -c user.name=... -c user.email=...`로 우회한다. 임의로 전역 설정을 바꾸지 않는다.

### 3. 문서 구조 제안 → 확인

- 번호 매긴 파일 목록을 제안하고 승인을 받는다. 기본 골격(주제에 맞게 가감):
  - `01-overview.md` — 개념 / 정의 / 목적 / 차별점
  - `02-architecture.md` (또는 `02-how-it-works.md`) — 동작 원리·구조
  - `03-usage.md` — 사용법 / 설치 / 기본 예시
  - `04-issues.md` — 이슈 / 한계 / 안티패턴 / 주의사항
- 주제가 **여러 대상의 비교**라면(예: 라이브러리 3종) 참고처럼 `<대상>/0N-*.md`로 디렉토리를 나눈다. 이 경우 README 인덱스의 링크 경로가 `./<대상>/01-*.md`가 됨에 유의(`templates.md`의 디렉토리 분리 예시 참고).
- 단순 주제면 문서를 줄이고, 복잡하면 늘린다. 과잉 분할 금지.
- **이 단계에서 구조를 승인받으면, 이후 문서별로 매번 승인을 다시 받지 않는다.** 작성한 문서를 보여주며 진행하고, 사용자가 멈추라고 하거나 방향을 바꾸라고 할 때만 멈춘다.

### 4. CLAUDE.md 작성·커밋 (레포 컨벤션 확정)

- git이 없으면 여기서 `git init -b main`.
- `CLAUDE.md`를 먼저 만든다: 레포 목적 + 작성 컨벤션(아래 **작성 원칙**을 명문화). 골격은 `templates.md`.
- 커밋: `git add CLAUDE.md` → `git commit -m "docs: CLAUDE.md 작성 규칙 추가"`. 이게 최초 커밋이 된다.
- 컨벤션을 먼저 박아두면 이후 문서가 일관된 형식을 따른다.

### 5. 문서 차례대로 작성 + 문서별 커밋

번호 순서대로 **한 문서씩** 작성한다. 한 문서를 쓰면 → (필요시 보여주고) → 그 문서만 커밋, 다음 문서로 넘어간다.

- 사실 주장은 출처를 확인하고 URL을 단다. 라이브러리/프레임워크/SDK/CLI는 `context7` MCP(`resolve-library-id` → `query-docs`)를 우선 사용하고, **context7가 없거나 해당 라이브러리가 없으면 `WebSearch`/`WebFetch`로 폴백**한다.
- 확신이 없으면 단정하지 말고 "확인 필요" 또는 "모름"으로 표기한다.
- **작성 원칙**과 **문서 구성 골격**(아래)을 지킨다.
- 문서별 커밋: `git add <그 문서 파일만>` → `git commit -m "docs: <주제> <문서명> 추가"`. **커밋 규칙**(아래) 참고.

### 6. 코드 예제 (필요 시)

- 코드 예제가 이해에 도움 되는 주제면 작성 여부를 확인한다. (1단계에서 합의했으면 건너뜀)
- **언어/프레임워크/라이브러리는 원칙적으로 1단계에서 이미 선택받았다.** 그 조합을 그대로 사용한다. (1단계에서 미뤘다면 여기서 1단계의 조사 → 선택 절차를 동일하게 수행한다)
- 작성 전 그 라이브러리의 **버전·API 시그니처를 `context7`로 재확인**하고(없으면 `WebSearch`), 예제가 실제 API와 맞는지 맞춰 쓴다.
- `examples/`에 실행 가능한 파일로 두거나, 짧으면 해당 문서 내 코드블록으로 넣는다. 언어를 코드펜스에 명시한다.
- 예제는 최소·실행 가능하게. 의존성/실행법을 한 줄로 적어 둔다.
- 언어에 따라 빌드 산출물이 생기면(`node_modules`, `__pycache__`, 빌드 폴더 등) 그에 맞는 `.gitignore`도 함께 둔다.
- `examples/` 파일도 `docs:` 프리픽스로, 관련 문서와는 **별도 커밋**한다. 예: `docs: <주제> 사용 예제 코드 추가`.

### 7. README.md 작성·커밋

- `README.md`: 한눈 비교/요약 표 + 문서 인덱스(각 문서로의 링크와 한 줄 설명) + 1차 출처 모음 + 조사 기준일(절대 날짜).
- 여러 대상을 디렉토리로 나눈 경우 인덱스 링크 경로를 `./<대상>/0N-*.md`로 정확히 적는다.
- 커밋: `git add README.md` → `git commit -m "docs: README 인덱스 추가"`.

### 8. 산출물 검증 + 보완 (반드시 수행)

이 시점엔 문서·코드·README가 모두 있다. **올바른지 스스로 검증하고 고친다.** 생략하지 않는다.

- **문서 검증**
  - 사실 주장이 단 출처와 실제로 일치하는지 1차 출처를 다시 확인한다(특히 숫자·버전·API 이름).
  - 내부 링크 확인: `README` → 각 문서, 문서 → 문서 상대경로가 **실제 파일을 가리키는가**. (디렉토리 분리 케이스의 경로 특히 주의)
  - 표/숫자/용어의 문서 간 일관성, 제목 계층(`#`→`##`→`###`) 준수, "확인 필요" 표기 누락 점검.
- **코드 예제 검증**
  - 가능하면 실제로 실행하거나 문법/타입 검사·린트를 돌린다(해당 언어 런타임·린터 사용).
  - 실행 불가 환경이면 import 경로·API 시그니처·버전 호환을 출처와 대조한다.
  - 통과하지 못하면 수정한다. 수정 못하는 한계는 문서에 "확인 필요"로 남긴다.
- **보완 반영**: 결함을 고친다. 이미 커밋된 파일을 고쳤으면 `docs: <대상> 보완` 커밋을 추가한다(문서별로 분리).
- 검증 결과(통과 항목 / 수정한 항목)를 사용자에게 **간단히 요약 보고**한다.

### 9. git 마무리

- 커밋 메시지는 전부 `docs: <한글 설명>` 형식이어야 한다.
- 커밋이 실패하면(예: pre-commit hook 거부, 설정 누락) 그대로 진행하지 말고 원인을 보고하고 사용자에게 확인한다.
- 마지막에 `git log --oneline`을 보여주고 전체 결과를 요약한다.

## 작성 원칙

사용자 전역 선호와 일관된 규칙이다.

- **사실 기반**: 사실 주장에는 가능한 한 1차 출처 URL을 단다.
- **추측 금지**: 확신 없으면 "확인 필요" 또는 "모름"으로 명시. 추측을 사실처럼 쓰지 않는다.
- **결론 우선**: 문서·답변 모두 결론을 먼저, 근거를 뒤에.
- **비교는 표로**: 선택지·개념이 여러 개면 비교표로 정리.
- **균형**: 권장 사항뿐 아니라 안티패턴·한계·주의사항도 함께 적는다.
- **언어**: 본문 서술은 한국어. 코드·식별자·고유명사·기술 용어는 원문 유지(예: tool use, MCP), 필요하면 한글 설명을 곁들인다.
- **제목 계층**: 문서당 H1(`#`) 1개 → `##` → `###` 순으로만.
- **날짜**: 절대 표기(예: 2026-06-10). "오늘", "최근" 등 상대 표현 지양.
- **범위 준수**: 요청 범위 안에서만. 문서 과잉 생성·과잉 리팩토링 금지.

## 문서 구성 골격

각 문서는 대체로 다음 흐름을 따른다(주제에 맞게 가감):

```
# <제목>

> 한 줄 핵심 요약(결론 우선).

## 개요 / 정의
## 핵심 내용 (표·인용으로 정리)
## 사용법 / 예시 (해당 문서면)
## 이슈 / 안티패턴 / 주의 (해당 문서면)
## 출처
- 1차 출처 URL들

---
*조사 기준일: <절대 날짜>. <신뢰도나 검증 메모>*
```

인용은 `> "원문" — 출처` 형식으로 단다.

## 커밋 규칙

- **문서 1개 = 커밋 1개.** 한 커밋에 여러 문서를 섞지 않는다.
- 커밋 전 `git add <해당 파일만>`으로 관련 파일만 스테이징한다(`git add -A`/`git add .` 지양 — 무관한 변경이 딸려 들어간다).
- 메시지 형식: `docs: <무엇을 했는지 한글>`
  - 예: `docs: NestJS DI 개요 문서 추가`
  - 예: `docs: 사용법 문서 보완`
  - 예: `docs: README 인덱스 추가`
- 커밋 메시지에 별도 서명/푸터를 넣지 않는다(결과물은 문서 레포이므로 간결하게).
- git user.name/email이 없으면 `git -c user.name=... -c user.email=...`로 우회 커밋(2단계 참고).

## 참고 파일

- `templates.md` — `README.md` / `CLAUDE.md` 스켈레톤, 문서 템플릿, 디렉토리 분리 케이스 예시, git 명령 메모. 골격이 필요할 때 읽어 사용한다.
