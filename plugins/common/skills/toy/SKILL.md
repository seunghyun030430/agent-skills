# toy

기술 주제 하나를 받아 **직접 만들고 실행하며 체득하는 작은 프로젝트**를 만든다.
문서로 이해하는 것은 `study` 스킬의 몫이고, 이 스킬은 **돌아가는 코드와 관찰한 사실**을 남긴다.

산출물은 **항상 현재 작업 디렉토리**에 만든다. 별도 경로로 옮기지 않는다.

핵심 태도는 다음과 같다.
- 실행해서 확인하지 않은 것은 "됐다"고 말하지 않는다.
- 설명보다 관찰을 남긴다(명령 → 출력 → 해석).
- 일부러 깨뜨려 봐야 이해한 것이다.
- 각 단계에서 애매하면 추측하지 말고 사용자에게 물어본다.

## study와의 차이

| 항목 | study | toy |
| --- | --- | --- |
| 산출물 | 번호 매긴 학습 문서 | 실행되는 프로젝트 + 마일스톤별 관찰 노트 |
| 최우선 가치 | 출처·정확성 | 실제로 돌아감·손으로 확인 |
| 단위 | 문서 1개 = 커밋 1개 | 마일스톤 1개 = 동작하는 상태 1개 = 커밋 1개 |
| 검증 | 1차 출처 대조 | 매 마일스톤 실행·테스트·관찰 |

## 워크플로

아래 9단계를 순서대로 따른다. **3단계에서 계획을 승인받으면, 이후 마일스톤마다 다시 승인받지 않고 끝까지 진행한다.** 단, 아래 **확인이 필요한 명령**은 그때그때 확인받는다. 사용자가 멈추거나 방향을 바꾸라고 하면 그때 멈춘다.

### 1. 주제·학습 목표·모드 확정

- 주제를 **한 줄로 확정**해 되읽어 준다. (예: "주제: Kafka consumer group과 리밸런싱")
- **체득할 핵심 개념 3~5개**를 제안하고 `AskUserQuestion`으로 합의한다. 이것이 마일스톤의 뼈대가 된다. 막연하면 무엇을 해 보고 싶은지 되묻는다. 임의로 시작하지 않는다.
- **구현 모드**를 묻는다.

  | 모드 | 코드 작성 | Claude의 역할 |
  | --- | --- | --- |
  | 데모 | Claude | 구현 → 실행 → 관찰 기록까지 수행. 사용자는 결과와 노트를 읽는다 |
  | 가이드 | 사용자 | 마일스톤마다 과제·`TODO`·힌트·검증 테스트를 준다. 사용자가 채우면 실행·리뷰하고 막히면 힌트를 한 단계씩 더 준다(정답을 바로 주지 않음) |

- 시간·난이도 감각(예: 1~2시간짜리 / 하루짜리)을 물어 마일스톤 수를 정한다.

### 2. 스택 선택

- 주제에 흔히 쓰이는 언어·프레임워크·라이브러리·실행 환경을 조사한다. 라이브러리/SDK는 `context7`(`resolve-library-id` → `query-docs`)로 실재·버전을 확인하고, 없으면 `WebSearch`/`WebFetch`로 폴백한다.
- 후보를 정리해 `AskUserQuestion`으로 선택받는다(각 선택지에 용도·차이 한 줄). 원하는 게 없으면 사용자가 직접 입력할 수 있게 한다.
- 원칙:
  - **로컬 실행 우선**(Docker Compose, kind 등). 클라우드 계정·비용이 드는 구성은 사용자가 원할 때만 쓴다.
  - **버전 고정**(이미지 태그, 패키지 버전, 도구 버전).
  - **최소 의존성**.
- 선택된 조합(및 버전)을 한 줄로 되읽어 확정한다.
- 로컬 도구 상태를 확인한다: 필요한 런타임·CLI가 있는지(`which`, `--version`), Docker 데몬이 떠 있는지. 없는 것은 목록으로 보고하고 설치 여부를 묻는다.

### 3. 마일스톤 설계 → 승인

번호 매긴 마일스톤 목록을 제안하고 승인받는다. 규칙은 다음과 같다.
- 마일스톤 하나는 **개념 하나**를 다루고, **실행 가능한 상태로 끝난다**(한 줄 실행 명령 + 기대 결과).
- 기본 골격(주제에 맞게 가감):

  | 마일스톤 | 내용 |
  | --- | --- |
  | M1 최소 구동 | 환경을 띄우고 가장 작은 동작(hello)을 확인 |
  | M2~M(n-2) 핵심 개념 | 1단계에서 합의한 개념을 하나씩 구현·관찰 |
  | M(n-1) **깨뜨려 보기 (필수)** | 아래 "깨뜨려 보기" 규칙 |
  | M(n) 정리 | 회고, 확장 아이디어, 정리 명령 |

- 각 마일스톤에 **완료 기준**(어떤 명령을 실행하면 어떤 출력이 나와야 하는지)을 적는다.
- 과잉 분할 금지. 1~2시간짜리면 4~5개, 하루짜리면 6~8개가 상한이다.

### 4. 스캐폴딩 + 최초 커밋

- 2단계 git 점검을 먼저 한다.
  - `pwd`로 위치를 보여 준다.
  - `ls -A`로 기존 파일을 확인한다. 덮어쓸 파일이 있으면 먼저 보고하고 확인받는다.
  - `git rev-parse --show-toplevel 2>/dev/null` 결과가 현재 디렉토리와 다르면 상위 레포 아래에 있는 것이다. 상위 레포에 커밋할지, 여기서 새로 `git init` 할지 묻는다.
  - `git config user.name`, `user.email`이 없으면 값을 묻거나 `git -c user.name=... -c user.email=...`로 우회한다. 전역 설정은 바꾸지 않는다.
- git이 없으면 `git init -b main`을 실행한다.
- 다음을 만든다. 골격은 `templates.md`를 따른다.
  - `README.md`: 목표, 마일스톤 표(상태 칸 포함), 요구 도구와 버전, 실행 방법, 정리 방법
  - `CLAUDE.md`: 이 레포의 규칙(모드, 마일스톤 규칙, 노트 형식, 커밋 규칙)
  - `.gitignore`: 언어·도구에 맞는 빌드 산출물과 다운로드물
  - 실행 진입점: `Makefile` 또는 `scripts/`. 마일스톤마다 `make m1`, `make m2`처럼 한 줄로 실행되게 한다.
- 커밋: `chore: 토이 프로젝트 스캐폴딩`

### 5. 마일스톤 반복 (M1 → M(n-2))

마일스톤마다 아래 루프를 돈다. **완료 기준을 통과하기 전에는 다음 마일스톤으로 넘어가지 않는다.**

1. **구현**
   - 데모 모드: Claude가 구현한다. 작성 전에 사용할 API 시그니처·버전을 `context7`(없으면 `WebSearch`)로 확인한다.
   - 가이드 모드: 과제 설명, `TODO` 주석이 달린 뼈대 코드, 완료 기준을 검사하는 테스트나 명령을 만든다. 사용자에게 구현을 요청하고, 사용자가 다 했다고 하면 다음 단계로 간다. 힌트는 한 번에 한 단계씩(방향 → 관련 API → 의사코드) 준다.
2. **실행**: 완료 기준 명령을 실제로 실행한다. 실패하면 원인을 찾아 고친다(가이드 모드에서는 원인을 짚어 주고 사용자가 고친다).
3. **관찰 기록**: `notes/0N-<slug>.md`에 남긴다(`templates.md`의 노트 골격).
   - 무엇을 실행했나(명령)
   - 무엇이 나왔나(핵심 출력 발췌)
   - 왜 그렇게 동작하나(해석, 근거 링크)
   - 예상과 달랐던 점
   - 개념 설명은 길게 쓰지 않는다. 필요하면 공식 문서나 `study` 문서로 링크한다.
4. **README 갱신**: 마일스톤 표의 상태를 ✅로 바꾼다.
5. **커밋**: 그 마일스톤 관련 파일만 스테이징한다. 예: `feat: M2 consumer group 리밸런싱 구현`, 가이드 모드 뼈대는 `chore: M2 과제 뼈대 추가`.

### 6. 깨뜨려 보기 (필수)

주제에서 흔한 오해·오설정·장애 시나리오 **2~3개**를 골라 각각 다음 순서로 진행한다.

| 순서 | 내용 |
| --- | --- |
| 가설 | "X를 하면 Y가 될 것이다"를 실행 **전에** 적는다 |
| 실험 | 오설정 주입, 프로세스·컨테이너 kill, 네트워크 차단, 권한 변경, 부하 등을 **재현 가능한 명령**으로 수행한다 |
| 관찰 | 실제 결과(출력, 로그, 수치)를 그대로 기록한다 |
| 해석 | 가설과 맞았는지, 틀렸다면 왜인지 설명하고 근거 링크를 단다 |
| 복구 | 원상태로 돌리는 명령과, 실무에서 막거나 감지하는 방법 |

- 시나리오 고르는 기준: 실무에서 실제로 사고가 나는 것, 흔히 퍼진 설명과 실제 동작이 다른 것, 기본값이 직관과 다른 것.
- 결과가 가설과 달라도 **고쳐 쓰지 않는다**. 그 차이가 가장 중요한 학습 결과다.
- 기록 위치는 `notes/0N-break-it.md`이고, 커밋은 `test: 깨뜨려 보기 실험 추가`다.

### 7. 정리 (마지막 마일스톤)

- `README.md`에 다음을 정리한다.
  - **배운 점** 3~5줄(관찰 기반)
  - 예상과 달랐던 것
  - 확장 아이디어(다음에 해 볼 것)
  - 정리 명령(`make clean` 등)
- 커밋: `docs: 회고와 확장 아이디어 정리`

### 8. 최종 검증 (반드시 수행)

- **깨끗한 상태에서 재현**한다. 가능하면 환경을 내리고(`make clean`) README의 실행 방법대로 처음부터 마일스톤 명령을 다시 돌려 통과하는지 확인한다. 오래 걸리면 사용자에게 범위를 묻는다.
- 린트·타입 검사·테스트가 있으면 실행한다.
- 링크를 점검한다(README → notes, notes → 외부 출처).
- 결함을 고치면 `fix: <대상> 수정`으로 커밋한다.
- 통과한 항목과 수정한 항목을 사용자에게 간단히 보고한다.

### 9. 마무리

- **띄운 리소스를 정리**한다(컨테이너, 클러스터, 포트포워딩, 백그라운드 프로세스). 사용자가 남겨 두길 원하면 남기고, 남긴 것을 목록으로 알린다.
- `git log --oneline`을 보여 주고 결과를 요약한다. 실행하지 못한 것, 검증하지 못한 것은 그대로 밝힌다.

## 확인이 필요한 명령

다음은 실행 전에 무엇을, 어디서, 얼마나 크게 하는지 밝히고 확인받는다(3단계 승인과 별개).
- 도구 설치: `brew install`, `npm i -g`, `pip install` 등 레포 밖에 영향이 가는 설치
- 파일 다운로드: 출처 URL과 대략의 크기를 밝힌다
- 사용자의 전역·영구 설정 변경: shell rc, git global, kubeconfig 컨텍스트 전환, Claude Code 설정
- 비용이나 외부 영향이 있는 작업: 클라우드 리소스, 외부 API 호출, 원격 push
- 삭제: 레포 밖 파일, 기존 클러스터·볼륨

레포 안의 작업(파일 생성, 로컬 빌드, 레포 전용 컨테이너·클러스터의 생성·삭제)은 3단계 승인 범위에 포함된다.

## 작성 원칙

- **실행 우선**: 모든 마일스톤은 한 줄 명령으로 실행되고, 완료 기준으로 판정된다.
- **관찰 기록**: 노트에는 실제 명령과 출력을 남긴다. 출력을 지어내지 않는다. 실행하지 못했으면 "미실행"으로 표기한다.
- **추측 금지**: 동작 원리를 확신하지 못하면 "확인 필요"로 표기하고, 가능하면 실험으로 확인한다.
- **결론 우선**: 노트와 README 모두 결론(무엇을 확인했나)을 먼저 쓴다.
- **최소 구현**: 학습 목표와 무관한 기능(인증, UI, 과도한 추상화)은 넣지 않는다.
- **버전 명시**: 도구·이미지·라이브러리 버전을 README에 적는다.
- **언어**: 본문 서술은 한국어. 코드·식별자·고유명사·기술 용어는 원문을 유지한다.
- **날짜**: 절대 표기(예: 2026-10-08).
- **범위 준수**: 합의한 마일스톤 밖으로 확장하지 않는다. 확장 아이디어는 README에만 적는다.

## 커밋 규칙

- **마일스톤 1개 = 커밋 1개**가 기본이다. 가이드 모드는 "과제 뼈대" 커밋과 "완료" 커밋으로 나눌 수 있다.
- 관련 파일만 스테이징한다(`git add <파일>`). `git add -A`나 `git add .`은 쓰지 않는다.
- 메시지는 Conventional Commits 형식에 한글 설명을 쓴다.

  | type | 용도 |
  | --- | --- |
  | `chore` | 스캐폴딩, 설정, 과제 뼈대 |
  | `feat` | 마일스톤 구현 |
  | `test` | 깨뜨려 보기 실험, 테스트 추가 |
  | `docs` | 노트·README 정리 |
  | `fix` | 검증 중 발견한 결함 수정 |

- 커밋이 실패하면(pre-commit hook 거부, 설정 누락 등) 그대로 진행하지 말고 원인을 보고한다.
